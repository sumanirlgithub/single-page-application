2. The most important interaction

The key design decision we made is:

The Kafka event contains the mandateId, but does not contain all the mandate information.

For example:

{
  "collectionId": "DD-20260930-000001",
  "mandateId": "MAND-20260930-000001",
  "amount": 500.00,
  "currency": "EUR",
  "requestedCollectionDate": "2026-10-15",
  "sequenceType": "OOFF"
}

The Payment Processor then asks the Mandate Service for the authoritative mandate:

Payment Processor
       │
       │ GET /api/v1/mandates/MAND-20260930-000001
       ▼
Mandate Service
       │
       │ MandateResponse
       ▼
Payment Processor

This avoids duplicating debtor/creditor information in Kafka.

  "currency": "EUR",

10. Responsibilities of each service
Service	Responsibility	Does it collect money?
Mandate Service	Create, store and retrieve mandates	No
Collection Service	Create direct-debit collection requests	No
Payment Processor	Process collection, retrieve mandate, generate pain.008, submit to bank/PSP	It initiates the bank collection; bank/PSP executes it
Kafka	Asynchronous event transport	No
Outbox	Reliable publication of collection events	No
Bank / PSP	Execute/process the SEPA direct debit	Yes

The architectural principle to remember

Mandate Service = "Who is authorized to collect?"

Collection Service = "What amount do we want to collect, and when?"

Payment Processor = "Turn that collection request + mandate information into a SEPA payment instruction and send it to the bank/PSP."
